# Развёртывание на REG.RU Host-0

В аккаунте подтверждён виртуальный хостинг Host-0 с ispmanager и доменом `maharussia.ru`. Этот вариант использует PHP и не требует VPS или Docker. Срок оплаты хостинга в карточке услуги — 31.07.2027; регистратор отдельно показывает уведомление о продлении домена, поэтому его фактический срок следует проверить в карточке домена.

## Подготовка в ispmanager

1. Для сайта выберите PHP 8.2 или новее. Проверьте `pdo_sqlite` (SQLite ≥3.24), cURL/OpenSSL с рабочим хранилищем доверенных сертификатов и DOM/XML для QR-кода. Разрешите исходящий HTTPS к `securepay.tinkoff.ru` и `api.cdek.ru`. Проверка TLS должна оставаться включённой. Расширения GD и mbstring не обязательны.
2. Проверьте доступность HTTPS для `maharussia.ru` и включите перенаправление HTTP → HTTPS средствами панели. Для `www` оставьте «Редирект домена» выключенным: правило в `.htaccess` переводит `www.maharussia.ru` прямо на `https://maharussia.ru`, сохраняя путь и запрос. Встроенный редирект панели на этом хостинге сначала отправлял HTTPS на HTTP. Сертификат должен покрывать оба имени.
3. Сохраните резервную копию существующего сайта. В карточке услуги уже есть занятые файлы и база данных: их содержимое нужно проверить перед заменой сайта.
4. Создайте приватную папку для базы и фотографий **вне корневой папки сайта**. Пример: `/var/www/USERNAME/data/mahara-private`, при сайте в `/var/www/USERNAME/data/www/maharussia.ru`. Замените `USERNAME` и проверьте фактические пути в панели. Доступ на запись нужен только пользователю PHP; для каталога достаточно прав 700.

## Содержимое поставки

`node tools/package-release.cjs` создаёт каталог с `site/`, этой инструкцией и manifest. Загружайте содержимое `site/` в корень сайта, включая `.htaccess` и `.user.ini`.

Не копируйте корневые `index.html`, `catalog.html`, `admin.html` и страницы товаров из рабочего репозитория: в поставке они уже перенесены в PHP-шаблоны. Это необходимо, потому что nginx на виртуальном хостинге может обслуживать существующие HTML-файлы до Apache и обходить `.htaccess`.

В `site/server/config.local.php.example` задайте фактический приватный путь и домен, затем сохраните как `server/config.local.php`. Минимальные настройки витрины:

```php
<?php
return [
    'data_dir' => '/var/www/USERNAME/data/mahara-private',
    'origin' => 'https://maharussia.ru',
    'production' => true,
    'trust_proxy' => false,
];
```

Origin указывается без завершающего `/`. Production отказывается хранить данные внутри публичной папки. Если провайдер завершает HTTPS на nginx и PHP не получает признак HTTPS, проверьте передаваемые параметры; `trust_proxy` включается только для доверенного прокси, перезаписывающего forwarded-заголовки.

## Первый администратор

Через SSH или терминал панели, находясь в корне сайта:

```sh
php tools/admin.php create
```

Укажите собственные логин и пароль. Для неинтерактивной настройки можно сгенерировать доступ в приватный файл:

```sh
php tools/admin.php create --generate --output /var/www/USERNAME/data/mahara-private/access.txt
```

Локальный пароль из `.local/preview-access.txt` не переносится на хостинг. Для замены пароля: `php tools/admin.php create --replace`; это также завершает активные сессии пользователя.

## Проверка после загрузки

- Главная и каталог открываются, CSS/JS/фотографии загружаются.
- `/admin.html` без входа перенаправляет на `/admin/login`; `/api/admin/session` возвращает 401.
- База, `server/`, `tools/`, `.git`, конфигурация и файлы доступа не доступны по HTTP.
- Новый товар с фотографией сохраняется и открывается отдельной страницей в другом браузере без административной сессии.
- В `/sitemap.xml` появился новый товар; отсутствующие страницы отдают 404.
- HTTPS работает, cookie сессии имеет HttpOnly, Secure и SameSite=Strict; HTTP и www перенаправляются на канонический HTTPS-домен.

## Обновления и резервные копии

Обновления заменяют код и шаблоны, сохраняя `server/config.local.php` и приватную папку данных. Не заменяйте рабочую базу новой пустой базой и не удаляйте приватные фотографии.

Для бэкапа SQLite и `uploads/` подготовлена команда. При SQLite ниже 3.27 требуется расширение PHP `sqlite3` с методом `SQLite3::backup` (проверено на Host-0 с SQLite 3.26.0):

```sh
php tools/backup.php create /var/www/USERNAME/data/mahara-backups
php tools/backup.php verify /var/www/USERNAME/data/mahara-backups/mahara-ДАТА-ИДЕНТИФИКАТОР
```

Создание использует SQLite `VACUUM INTO` при версии 3.27+; для более старой версии — нативный Online Backup API через отдельное соединение к рабочей базе только для чтения. Оба варианта включают зафиксированные записи WAL, затем копируются фотографии. Если безопасный API недоступен, команда завершается ошибкой; обычного копирования живого файла базы нет. Проверка сверяет SHA-256 файлов и целостность SQLite. Путь вне сайта обязателен; база, фотографии и manifest приватны. Команда не удаляет старые бэкапы и не восстанавливает рабочую базу автоматически. Права каталога 700, файлов 600; отдельно организуйте шифрованную копию приватных настроек и секретов, которые в snapshot не включаются. Срок хранения и страну размещения копий согласуйте с владельцем.

Для пробного восстановления остановите PHP тестового сайта, поместите копию `mahara.sqlite` и `uploads/` в его отдельный приватный `data_dir`, запустите с отключёнными платежами/доставкой/почтой и проверьте каталог, склад и заказы. Рабочие данные не заменяйте без отдельного решения. При необходимости переноса живой базы никогда не копируйте только `mahara.sqlite` без учёта WAL.

Поставка включает исходный каталог. Рабочее содержимое хранится в SQLite отдельно от кода: его перенос выполняется приватной резервной копией вместе с фотографиями.

## Настройка оплаты и доставки

Для запросов к фиксированному API Т-Банка поставляется `server/certs/tbank-ca.pem`: стандартный набор Mozilla из [curl.se](https://curl.se/docs/caextract.html) и Russian Trusted Root CA из официального архива Госуслуг `https://gu-st.ru/content/lending/linux_russian_trusted_root_ca_pem.zip`, загруженные 10.10.2026. Этот файл применяется только к банковским запросам и не меняет доверенные сертификаты ОС или соединений СДЭК. Не удаляйте его из поставки; обновляйте при изменении требований банка и корневых сертификатов. [Требования Т-Банка](https://developer.tbank.ru/eacq/intro/certificates/). HTTPS-соединение с банком проверено локально без ключей и платежей; такая проверка не подтверждает активацию терминала.

Реквизиты можно сначала сохранить и проверить отдельно от включения оплаты. Из корня сайта в терминале хостинга выполните:

```sh
php tools/tbank.php save-terminal
php tools/tbank.php check-terminal --saved
```

Первая команда спрашивает ключ и скрытый пароль, сохраняет их только в приватный `data_dir/tbank-secrets.php` с правами 600 и отказывается заменять существующий файл без явного `--replace`. Не вводите пароль как аргумент команды. Вторая команда с явным `--saved` использует сохранённые реквизиты для единственного запроса [CheckOrder](https://developer.tbank.ru/eacq/api/check-order) со случайным номером отсутствующего заказа: платёж и заказ не создаются, настройки оплаты и остатки не меняются. Вывод содержит только итог диагностики и безопасный код ответа; отсутствие заказа само по себе не доказывает правильность пароля. Эта проверка не подтверждает СБП или формирование чеков. Итоговую готовность checkout показывает `php tools/commerce.php status`.

1. В приватной папке `data_dir` создайте `tbank-secrets.php`, возвращающий массив `['terminal_key' => '...', 'password' => '...']`, и `cdek-secrets.php` с `['account' => '...', 'password' => '...']`. Права на файлы — 600. Не загружайте локальные секреты в публичный каталог и не передавайте их через URL.
2. Перенесите блоки `payments` и `shipping` из примера конфигурации. Укажите фактические город отправления СДЭК, разрешённые тарифы доставки до ПВЗ и вес/габариты упакованной вещи для каждой категории. Текущий расчёт считает каждую вещь отдельным местом. Доставка оплачивается получателем; её оценка не входит в сумму СБП.
3. В Т-Кассе проверьте, что терминал предназначен для этого сайта, СБП включена и подключён сервис чеков. Задайте реальные `taxation`, `item_tax` и опубликованные ссылки `terms_url`, `privacy_url`. `receipt_enabled=true` означает подтверждённую настройку кассы владельцем, а не автоматическую проверку кассы приложением.
4. Сначала проверьте тестовый терминал: создание заказа, QR/ссылка СБП, подписанное уведомление, статус и единственное списание склада. Адрес уведомления: `https://maharussia.ru/api/payments/tbank/notify`. Для тестового и рабочего режима используются соответствующие отдельные данные терминалов. Автоматические тесты проекта не обращаются к банку и СДЭК.
5. Проверьте `php tools/commerce.php status`, затем включите `shipping.enabled` и `payments.enabled` для проверенных настроек. Перед продажами внесите фактические остатки и выполните согласованную с владельцем проверку рабочего терминала. Не считайте переход на страницу успеха подтверждением оплаты.

Проверка состояния заказа на сайте ограничивает частоту обращений к банку. При недоступном банке резерв сохраняется: истечение локального времени само по себе не освобождает оплачиваемый товар. Для обслуживания зависших заказов можно вызывать `php tools/commerce.php reconcile --limit=1` из приватного задания планировщика; команда не отменяет платежи и не инициирует возвраты. Заказы с неясным статусом нужно сверять в кабинете Т-Кассы. Автоматический возврат из-за истечения времени не выполняется.

Заказы управляются в `/orders.html`. Создание накладных СДЭК выполняется отдельно. При оплате передаётся чек полной предоплаты; фискальный результат проверяется в сервисе кассы. Закрывающий чек при передаче товара, маркировку и кассовый процесс возврата необходимо настроить в кассовом сервисе: автоматический закрывающий чек не реализован.

## Документы и почта перед запуском

Заполните блок `merchant` из примера конфигурации: ФИО ИП/наименование, ОГРНИП/ОГРН, ИНН, адрес, контакты, адрес возврата, условия оплаты/доставки и фактическое обращение с данными. Проверьте все пять информационных страниц. После одобрения владельцем укажите версию и `published=true`. Встроенные `/terms.html` и `/privacy.html` в состоянии черновика блокируют оплату, включая их абсолютные URL на этом домене. Принятие версии условий сохраняется в заказе; для архива храните одобренные версии конфигурации/текстов отдельно вместе с бэкапами.

Проверьте с владельцем уведомление Роскомнадзора, размещение основной базы и копий, сроки хранения и порядок удаления, фактических получателей данных (банк, кассовый сервис/ОФД, перевозчик, хостинг, почта), наличие трансграничной передачи. Технический шаблон политики не подтверждает выполнение этих действий магазином.

Для служебных писем задайте `mail.enabled`, SMTP-host, порт 465/TLS или 587/STARTTLS, адрес отправителя и почту магазина. Данные авторизации храните в `data_dir/mail-secrets.php`: массив `username`/`password`, права 600. Проверьте домен отправителя, SPF/DKIM/DMARC и доставку в почтовом сервисе. После согласованного теста письма запускайте `php tools/notifications.php send` через закрытый cron раз в минуту; за запуск обрабатывается до трёх писем. Ошибки отражаются счётчиком, секреты и адреса не печатаются. После восьми неудачных попыток запись остаётся `failed` для проверки оператором. Письма о заказах не являются кассовыми чеками.

Добавьте отдельные задания cron: сверка банка `php tools/commerce.php reconcile --limit=1` раз в минуту, резервная копия `php tools/backup.php create /АБСОЛЮТНЫЙ/ПРИВАТНЫЙ/ПУТЬ` ежедневно. Для каждого задания задайте рабочий каталог сайта и путь к PHP хостинга. Не используйте публичные HTTP-адреса для cron. Настройте контроль ненулевых кодов возврата/failed и заполнения диска средствами хостинга, а сроки хранения бэкапов — по подтверждённой политике магазина.
